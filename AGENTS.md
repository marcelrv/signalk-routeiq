# Project Conventions for AI Agents

## Architecture: Server-Side Routing, Frontend Is a Client

- **All routing logic lives in the SignalK server plugin** (`packages/routeiq-core/src/routing.ts`, `packages/routeiq-core/src/database.ts`, `packages/routeiq-core/src/db-worker.ts`). The A* search, graph loading, constraint evaluation, LOS smoothing, and violation reporting all run server-side.
- **The frontend** (`public/index.html`) is purely a **client** — it defines waypoints (start/dest/via), displays the calculated route on a map, and provides a graph editor. It contains zero routing logic. It must never implement its own pathfinding, graph traversal, or constraint evaluation.
- **The API** (`POST /signalk/v1/api/router/route`) is the single entry point for route calculation. It returns a `FeatureCollection` with per-segment features, each annotated with `minDepth`, `maxAirDraft`, `costFactor`, etc., plus violation warnings. This API is designed to be consumed by **any frontend** (the built-in one, third-party UIs, mobile apps, etc.) — it is not coupled to the Leaflet UI.
- **Route simplification and itineraries are backend concerns** (`packages/routeiq-core/src/itinerary.ts`, invoked from `RoutingEngine.finalizeRoute`). Every route result also carries `waypoints` (Douglas-Peucker-simplified navigable points, max deviation = `waypointTolerance` config, default 30 m; each via's vertex is always kept, and the start/via/end waypoints carry `kind` + `viaIndex`) and `itinerary` (start/via/end + major turns with per-leg distance/minDepth/minWidth/maxAirDraft aggregates and crossings with `distanceFromStart` chainage; each point's `coordIndex` is its route vertex, feature k running from vertex k to k+1). The start and end entries also carry `name` + `nameSource` (`nameEndpoints` in `packages/routeiq-core/src/route-description.ts`): the nearest named POI within 250 m (`nearestPoiName`, a part reads as its whole), else the named water the route starts/ends in (within 500 m of the end); clients use it only when they have no name of their own for that end. Frontends must render these, never re-derive them from geometry (the webapp's client-side `extractMajorNodes` is legacy and should migrate to `itinerary`).
- **Route description** (`packages/routeiq-core/src/route-description.ts`, `packages/routeiq-core/src/route-metadata.ts`, `describeRoute` in `packages/routeiq-core/src/db-worker.ts`): after a route is found, the worker reads `edge_sequence_id`, water bodies, names and NAVLINE notices for the route's edges only; nothing goes into the in-memory graph and the `loadEdges` SELECT stays untouched. The result is `RouteResult.description` plus `ItineraryPoint.leg.waters` (UIs render, never recompute); every warning there, and every shallow/narrow `leg.warnings` entry (`legWarnings` in `packages/routeiq-core/src/itinerary.ts`, against the request's vessel dims), carries a server-decided `level` (`danger`/`caution`/`info`) that clients show as sent, and may carry `at` (`RouteLocation[]`: vertex range + chainage + bounds, a point when `coordIndex === toCoordIndex`) saying where it applies — clients link a warning to the map from `at` alone, never by its `type`, so a new warning type needs no client change; `lang` comes in on the route request. Tables are detected per file, not by `schema_version`; old files just have no description. Depth quality is compared by `rank` against the `'charted'` row (never by id), unknown enum ids read as `other`/`unknown`, and none of it is ever a routing cost. Colliding sequence/water-body ids between files switch that file's description off (`descriptionError` in `GET /databases`) but it still routes. Departure scans pass `describe: false`.
- **Passage profile** (`packages/routeiq-core/src/passage-profile.ts`, issue #50, format in `docs/passage-profile.md`): a saved route resource carries `feature.properties.passageProfile`, holding the calculated duration (total includes waiting), the waits, dated departure/arrival or `null`, and the assumptions (`RouteResult.calculatedAt`/`timingAssumptions`, set in `finalizeRoute`) and warnings, tied to the saved geometry by `geometry.hash` (`geometryHash`, 1e-5° integers). The server builds it: `/push` writes it with the route, and for the Freeboard panel, whose host saves the route itself, the panel sends its last result to `POST /router/route/profile` on `route.saved`, and the server attaches the profile only when the stored geometry still hashes the same (409 otherwise). `toGpx` writes the same profile as `ar:` extensions in `<rte><extensions>` (no hash) and adds the duration to `<desc>`. Clients forward the result and never build a profile. Bump `PASSAGE_PROFILE_VERSION` on a change that would break a reader.
- **Engine options and per-request inputs** (`packages/routeiq-core/src/engine-options.ts`, `request-validation.ts`; plugin side `src/engine-options.ts`, `src/vessel-state.ts`): `RoutingEngine` takes `EngineOptions` (search tuning plus defaults), never `PluginConfig`, and keeps no vessel or user state. `resolveRouteInputs(request, options)` builds one `RouteInputs` per request (and per departure scan) — draft/beam/airDraft, speed, safety margins, waits, tides, coast distance, `lang`, `describe`: request value, else option default — and it is passed down the search; it is echoed as `RouteResult.inputs` with `coreVersion`. `requireVesselInRequest` (strict mode, off in the plugin) makes a request without draft, beam, airDraft and `speedKnots` throw `RouteRequestError` (`VESSEL_INCOMPLETE`). The plugin owns the vessel (`VesselState`: Signal K stream values and `PUT /vessel`) and `fillRequest` puts it, the configured speed and the margins into every route and departure-scan request before the engine sees it; a request value wins. `toEngineOptions(config)` maps `PluginConfig` onto the options. `validateRouteRequest` (core) is the shared request validator; the plugin calls it with its limits (`PLUGIN_REQUEST_LIMITS` in `src/api.ts`) and `validateRequestConstraints` is a thin wrapper over its `checkRequestConstraints`.
- **Logging, codes, messages, failures, counters** (`packages/routeiq-core/src/logger.ts`, `codes.ts`, `messages.ts`, `failure.ts`, `counters.ts`): core never touches the console; it logs through the injected `Logger` (`EngineOptions.logger`, `RoutingDatabaseOptions.logger`; the db worker thread forwards its calls to `SqliteWorkerStore`, which hands them to the logger). `src/logger.ts` is the plugin's logger and prints exactly what core printed before (all levels, `debug` included, to `console.log`/`warn`/`error`). At `info` and above a log call carries no route coordinates, request bodies or user-entered names; anything that locates a route or position (a vessel position, a node id) is `debug`. Every warning, leg warning, description warning, crossing note (`noteCode`/`noteParams`), departure scan error and failure carries a stable `code` + `params` (numbers in metres/seconds, plus ids and names); `type` fields stay as they are. All user-facing text is rendered from the catalogue (`format(key, params, lang)`, en + nl): add the English text and the Dutch text there, never a template in an engine file. The English wording is the reference and must not change by accident (the goldens and `test/observability.test.ts` pin it). `EngineOptions.messageLanguage` is `"request"` (follow the request `lang`) or a fixed tag; the plugin maps it to `"en"` because both UIs are English, while `lang` still picks water names. A failed route throws `RouteFailure` (codes in `FAILURE_CODES`; `RouteSearchError` is the subclass the bounding-box loop retries on; a plain `RouteFailure` keeps `name` `"Error"`). Its message never has a file path, SQL, a stack trace or an internal id: that goes to the logger. The plugin's 422 body is `{ error, code: "ROUTE_NOT_FOUND" | "SCAN_FAILED", failure?: { code, params, blocking? } }`. `RoutingEngine.getCounters()` gives cumulative numbers, nothing per request.
- **Graph editor endpoints** (`/signalk/v1/api/router/graph/nodes/*`, `/signalk/v1/api/router/graph/edges/*`) expose CRUD for the routing graph for debugging and manual corrections, but all actual routing decisions remain server-side.
- **Vessel dimensions** (draft, beam, airDraft) are fetched from the SignalK delta stream on the server and injected into the routing engine. The frontend may display them but does not enforce constraints.
- When modifying the frontend, ensure no routing logic leaks into it. The frontend should only: collect waypoint coordinates, POST them to the API, render the returned GeoJSON, and display warnings/metadata.
- **README is rendered by the Signal K App Store** (from the published npm package), which escapes all HTML, comments included: `<!-- -->` and `<img>` show as literal text there. Keep `README.md` plain Markdown with no HTML at all, and use absolute `raw.githubusercontent.com` URLs for images (relative paths do not resolve on npmjs.com or in the App Store).
- **Browser floor**: the webapp runs on old chart plotters, so it targets `browserslist` in `package.json` (currently Chrome/WebView 66). `npm run lint` checks `public/app.js` against it, but that check has gaps — **ask before introducing anything that raises the minimum**.
- **Chart sources** (webapp, "chart sources" section in `public/index.html`): the Charts tab lets users pick map layers — built-in OSM/OpenSeaMap plus charts from the SK server's `resources/charts` API (fetched from the *server root*, not the plugin router mount). Raster `tilelayer` charts render via `L.tileLayer`; S-57 `pbf` charts via Leaflet.VectorGrid with a **simplified** S-52 day-palette style. That normalisation + styling is adapted from Freeboard-SK (Apache-2.0) — keep the attribution comments there and in README when touching it. Selection persists in `localStorage['routeiq-charts']`.

## Freeboard-SK Plotter Extension (plotterext/)
- The plugin is also a **plotter extension provider** (Plotter Extensions API v1, see the Freeboard-SK docs). `src/plotterext.ts` registers a read-only `plotterExtensions` resource manifest (toolbar button + `routeiq-panel` iframe panel) and mounts assets at `/plotterext/signalk-routeiq/`.
- The panel (`plotterext/panel.html` + `panel.js`) has **no map** — the host chartplotter renders everything. It reads the visible route via the host `routes` capability (`route.list`/`route.get`), POSTs first/middle/last points as start/via/end to `POST /router/route`, stages the result with `route.replace`, and persists via `route.save({dialog:true})`. Same rule as the webapp: zero routing logic client-side.
- **Which route points are vias**: the host keeps nothing but each point's name, description and href across a save (Freeboard rebuilds `feature.properties`), so the panel marks the request points by name. It names the start/via/end waypoints (the server's `waypoints[].kind`; an unnamed via becomes `Via n`) and the points in between `WPn`; `isFillerPoint` reads `WPn` without an href as generated. `currentRequestPoints` reuses the session's request points while the route is unchanged, and otherwise diffs the route against the last calculated (`session.generated`/`requestAt`) or loaded (`baselines`) points: points still in place keep their role, moved or added points become vias, generated points are dropped (`deriveRequestPoints`).
- Chart actions (`actions` capability: Set start / Add via / Set destination, Optimise route / Best departure time) and the panel's 📍 pick buttons (`map.pick`) only hand the panel coordinates or a route handle; a plan becomes a draft route via `route.create` once start and destination are known. Every capability newer than the original set goes in the manifest's `optional` list (an unknown id in `requires` makes the extension incompatible with that host), and the panel gates each use on `client.hasCapability()`.
- The `signalk-plotterext-bus` client library (npm dependency) is served from its `node_modules` dist at `/plotterext/signalk-routeiq/bus/`; the panel imports `./bus/extension.js`.
- Extension assets are deliberately **not** under `/plugins/*` (admin-gated) and the package must **not** rely on the `signalk-webapp` keyword for them.
- `averageSpeedKnots` (with the lock/bridge waits and `considerTides`) is exposed to clients via `GET /router/config`; ETA in both UIs derives from the plugin-config average speed.

## Bounding-Box A* Search (runtime)
- `packages/routeiq-core/src/routing.ts:astarSearch()` accepts an optional `bbox` parameter that prunes nodes outside the box.
- On failure, the margin doubles (`routingBBoxMargin` → `routingBBoxMaxExtent`).
- BBox expansion adds warnings to the route result.
- Via points each get their own per-segment bounding box.

## Request Budget, Abort and the Worker Host (`routeiq-core`)
- **Budget**: `EngineOptions.budget = { maxIterations, maxWallMs }` (default unlimited) is spent over a whole request (every bbox retry, via leg, departure-scan step, smoothing). `calculateRoute`/`streamDepartures`/`scanDepartures` take `{ budget, signal }` as call options (`RouteCallOptions`); a call's budget can only lower the option. Overrun throws `RouteFailure` `BUDGET_EXCEEDED` (params `limit`, `used`, `max`; counted in `budgetHits`). The per-search cap `EngineOptions.maxSearchIterations` (5_000_000) is separate and still ends a search as "no path" with `iterationLimit`. Checks sit in `astarSearch`'s loop and between retries/legs/steps (`checkStop` in `routing.ts`, state in `request-control.ts`); any `catch` that retries or falls back must rethrow `isStopFailure(e)`.
- **Abort**: the same call options take an `AbortSignal`; an aborted request throws `ABORTED`. The NDJSON departure stream in `src/api.ts` aborts an `AbortController` when the client disconnects.
- **Worker host** (`worker-host.ts`, run by `EngineClient` from `engine-client.ts`): the engine in a `worker_thread`, so a long search stays off the caller's event loop and a crash or hang is contained. Protocol in `protocol.ts` (`PROTOCOL_VERSION`, closed request set `HOST_REQUEST_TYPES`: no message lists the graph, edges or all POIs). One job at a time, queued by the client; `abort(jobId)` or a signal cancels a queued job at once and signals a running one; `hardStopGraceMs` terminates and replaces a worker that outlives its `maxWallMs`, rejecting that job (`WORKER_RESTARTED`) while queued jobs run on the new worker. GPX is built only from the last 32 results the host holds (by result id). Bundled as `dist/worker-host.js` (`scripts/bundle.mjs`).
- **The plugin stays in-process**: `src/` calls `RoutingEngine` directly and does not use `EngineClient`; it only passes a real `AbortSignal` to the departure scan. Tide providers are not available in the host.

## Deterministic Node IDs (coordinate hashing + type packing)
- Node IDs are globally unique integers derived from snapped (lat, lon) at 5 decimal places + node type.
- Formula: `lat_int = int((round(lat,5) + 90.0) * 100000)` (0..18M), `lon_int = int((round(lon,5) + 180.0) * 100000)` (0..36M), `type_int = 1 if 'inland' else 0`.
- `id = (type_int * 648_000_000_000_000) + (lat_int * 36_000_000) + lon_int`.
- Fits within `Number.MAX_SAFE_INTEGER` (53 bits). Allows merging multiple regional `.sqlite` files without ID collisions.
- On the TypeScript side, use `getNodeTypeInt(id)` (`Math.floor(id / 648000000000000)`) to extract the type (0=coastal, 1=inland) without loading a string column.
- No `node_type` column in SQLite — the ID encodes the type at all times.
- POI ids are opaque: the producer keeps them stable across builds and they are no longer recomputable from the position. Compare them only for equality; ids are comparable only between files of one producer.

## SQLite Schema
- **`metadata`** table: `country`, `name`, `description`, `last_update_date`, `tags` (JSON array), `bounding_box` (JSON), `boundary_geometry` (GeoJSON), `schema_version` (4 for the POI model), `format_generation` (0 for now), `contributor`, `url` — describes the data source. `country` is no longer UNIQUE (a country may have multiple region databases).
- **`edge_type_enum`** table: `(id, description)` — `0=coastal, 1=inland`.
- **`poi_type_enum`** table: `(id, description)` — `0=harbour, 1=lock, 2=bridge, 5=lock_chamber, 6=bridge_span` (the enum table may list more ids; routeiq handles only these five, see POI Model).
- **`nodes`** table: includes `region_id INTEGER REFERENCES metadata(id)` for per-region replacement. No `node_type` column — type is encoded in the node ID (see above).
- **`edges`**: uses `edge_type_id INTEGER` (FK to `edge_type_enum`) and `traffic_mode INTEGER` (`0=two-way, 1=one-way fwd, 2=one-way rev`). No `direction_penalty`, `edge_type` TEXT, `is_one_way`, or `traffic_dir` columns. No region-level column needed (edges follow their source node's region).
- **`pois`**: `(id, type_id, name, lat, lon, parent_id, properties JSON, info JSON, region_id)`. The same whole or part can be in several files with the same id and content; routeiq keeps one entry per id.
- **`edge_pois`**: `(source, target, poi_id)`, `source < target`: the parts (chambers, spans) an edge passes. Read for the edges of a found route, never at start-up.
- `edges.lock_id` and `properties.structure` no longer exist.

## POI Model (spec §1.1, §2.10, §2.14; routeiq reads nothing else)
- **No legacy path.** A file is refused at open (`formatRefusal` in `packages/routeiq-core/src/db-worker.ts`) when `metadata.format_generation` is not in the supported set `{0}` (missing column = 0), or when it predates the model: `schema_version` < 4, no `pois.parent_id` column, or no `edge_pois` table. The refusal is per file and never fatal for the others: `GET /databases` lists it with `state: "unsupported"` and a `formatError` message ("rebuild it with the factory"), like `descriptionError` for the description; it is skipped by every region-selection path. `loadDatabaseGraph` of such a file rejects with the message. There are no fallbacks: do not read display keys from `properties`, do not reintroduce `lock_id`.
- **Wholes and parts.** Types: `0` harbour, `1` lock (whole), `2` bridge (whole), `5` lock_chamber (part), `6` bridge_span (part). A part's `parent_id` is its whole (one level); a bridge_span can have a lock as parent (a span over a lock head). A route passes parts and is reported as passing the whole. A part whose parent is not loaded is treated as a whole of its own. Rows of any other `type_id` are dropped at load. Constants and the `KNOWN_POI_TYPES`/`POI_PART_TYPES`/`POI_WHOLE_TYPES` sets are in `packages/routeiq-core/src/database.ts`; `getPoiParent`/`getPoiChildren` give the parent and child maps.
- **`properties` (routing keys only)**: `subtype`, `closed_height`, `typical_wait_minutes`, `opening_hours`, `clearance_reference`, `underside_nap`, `mhw_nap`. `typical_wait_minutes` is on wholes; also on a chamber (overrides the lock's value, `0` is a real value) and on a span whose parent is a lock; a span under a bridge whole reads the whole's. Loaded for every POI at start-up; every `JSON.parse` of it goes through `parsePoiJson` (a bad row reads as `{}`).
- **`info` (display keys)**: `kind`, `height`, `height_unknown`, `height_source`, `chart_height`, `refs`, `sources`. Never loaded at start-up: the worker message `poiInfo {ids}` reads it on demand; `getPoisInBBox` (at most 500 results), `searchPois`, `getNearestPoi` and the crossings carry it as its own `info` field beside `properties`. Server and UI read heights and kinds from `info` only. A bridge span's structure kind (`bridge`, `cable` = overhead power line, `weir`, ...) is resolved by the server (`spanKind`: the span's own `info.kind`, else its bridge whole's) and sent as `kind` on map POIs and bridge crossings; `height_unknown` is resolved the same way (`spanHeightUnknown`) and sent as `heightUnknown` on both. Clients take an absent kind as a bridge and never walk to the whole themselves. A crossing group (one whole) can mix kinds, since a span's own kind wins: clients draw the bridge from its non-cable spans and add a pylon badge, never pick by the first entry.
- **Map and search.** The map (`GET /pois`) returns parts and harbours (with `displayName`: the whole's name for a chamber or a span of a bridge); search returns wholes and harbours. Neither shows a thing twice.
- **Crossings.** `detectRouteStructures(coordinates, segments)` expands the route's segments into graph edges (`expandSegmentEdges`, shared with the route description), makes one `routePois {pairs}` request (pairs normalised to (min, max); the union of `edge_pois` over every file that holds the pair, with a `known` flag; a file with no `edge_pois` row at all has linked nothing and has no say, so on its own the pair is unknown), and lists exactly the chambers and spans linked to the route's edges, grouped by `parent_id`. On an edge no file holds (connector, navmesh shortcut, overlay edit: `known` false) it falls back to geometry for that edge only (in an aggregated segment, the line between that edge's nodes; the known edges keep their links): parts within `FALLBACK_MAX_DIST` (50 m, point-to-segment distance to that line; was 150 m from a vertex, which listed bridges on neighbouring canals, #57). A crossing carries the whole's name, `structure` = the whole's id as a string, and `partId` = the chamber or span used (the one nearest the line). The wait is the part's own value where the spec lets it carry one, else the whole's. Each crossing also carries `passage` (0, 1, ... in route order, per type and `structure`): one pass is one merged run of consecutive route edges linked to the structure (runs closer than `MERGE_ROUTE_DIST` merge, unless the route turned back between them); a run after a turn-back is the next index, and so is a run beyond that gap except under a lock whole, which is passed twice only by turning back (the spans over both heads of a long lock are one pass) (#60). `groupCrossings` (the waits) uses the same index: another pass of a structure already in a group starts a new group, the same pass listed twice stays in it. Clients group a leg's crossings by `type` + `structure` + `passage` (an absent `passage` reads as one pass), so two passes inside one itinerary leg stay two rows; `distanceFromStart` is never the key. The result is not cached between routes: a departure scan asks once per evaluated route.
- **Lock spans.** The same request sets `segments[].lockIds` to the lock whole of each linked chamber, or of a linked span whose parent is a lock. `crossingWaitSchedule` turns those into lock spans.

## Database layer (`packages/routeiq-core/src/database.ts`, `packages/routeiq-core/src/db-worker.ts`, `packages/routeiq-core/src/route-metadata.ts`)
- `RoutingDatabase` takes `RoutingDatabaseOptions` and knows no plugin data directory. It is told which region files exist (`files`: a list of `{path, enabled, name?}` or a function returning one, called by `init` and `reloadMetadata`); the directory scan, the `.disabled` suffix, the `user-edits.sqlite` exclusion and the auxiliary GeoJSON paths are in the plugin-side `src/data-dir.ts` (`directoryDatabaseOptions`, `createDirectoryDatabase`). Coverage-index keys are `entry.name` (the plain `.sqlite` filename).
- Persistence goes through `RoutingStore` (read side) and the optional `OverlayStore` (graph edits), both in `packages/routeiq-core/src/routing-store.ts`; `SqliteWorkerStore` (`packages/routeiq-core/src/sqlite-worker-store.ts`) is the SQLite implementation and keeps the worker thread and its message protocol. A store can be anything that answers the same calls (the tests use an in-memory one).
- `policy`: `dynamic` (load on demand, LRU caps), `pinned` (`loadGraph` loads every enabled region; nothing loads or evicts on demand; caps ignored) or `bulk` (the original load-everything path). `readOnly: true` opens region files read-only, opens no overlay, writes nothing, and every graph edit rejects with `GraphEditError` (`READ_ONLY`; `NO_OVERLAY` when no overlay is configured).
- `checkCoverage` answers from the coverage index alone; `getStatus()` is the structured per-file status; `getDataVersion()` is the loaded files' name + `last_update_date`, echoed on a route as `inputs.data`.
- These modules import nothing plugin-specific (no `@signalk/*`, `express`, `src/types.ts` plugin config): types come from `routeiq-core`.

## Config
- `routingDataDir` (was `routingDatabase`): path to a **directory** containing one or more `.sqlite` routing graph files.
- `routingBBoxMargin` (deg, default 0.1): initial bounding box margin
- `routingBBoxMaxExtent` (deg, default 10.0): max bbox before full-graph fallback
- `lineOfSightSearchRadius` (m, default 0 = smoothing off): LOS node search radius. Internal.
- **Retired settings** (`RETIRED_CONFIG_KEYS` in `src/types.ts`): `start()` deletes these from the saved config before merging defaults, so a value saved when the field was on the settings page never applies. Listed there: the internal tuning keys (`routingBBoxMargin`, `routingBBoxMaxExtent`, `lineOfSightSearchRadius`, `waypointTolerance`, `eagerLoadAtPosition`, `loadRadiusNm`, `maxLoadedRegions`, which keep fixed `DEFAULT_CONFIG` values) and the removed ones (`wrongWayPenalty`, `lineOfSightSampleInterval`, `defaultCoastDistance`, `maxTidalCurrentKnots`). Retiring a setting = remove it from `schema()` and add it here; a test checks the schema offers none of them.
- **No coast-distance default**: a route keeps a coast clearance only when the request sends `minCoastDistance` (nm). Factory databases carry no `distance_to_land` (it reads 9999), so a server default did nothing there.
- **Tides** (`packages/routeiq-core/src/tides.ts`: the `TideHeightProvider`/`CurrentProvider` interfaces and the field math; the Signal K clients `TidesClient`/`CurrentsClient` are in `src/tide-providers.ts`): currents come only from `signalk-tidal-currents` stations (`prepareStationFlowField`; zero flow beyond 20 km of a station). `signalk-tides` supplies heights only (`prepareTideHeights`), for depth at passage. With heights but no current stations, `RouteResult.tide.source` is `"heights"` and the flow is zero (`noCurrentField`). Never estimate a current from heights again.
- **Reaching the tide plugins** (`src/server-access.ts`, `src/tide-providers.ts`): no setting. `signalk-tidal-currents` is called in-process through its `currentsApi` PropertyValue (version 1: `findStations(lat, lon, limit)`, `getTimeline(id, startIso, endIso, stepMinutes)`, same JSON as its HTTP routes; `watchCurrentsApi` in `start()`). Otherwise, and always for `signalk-tides`, it is an HTTP loopback to `localServerBase(app)` (https on the ssl port when `settings.ssl`, else http on the port; `PORT`/`SSLPORT` win, like the server's ports.js), with certificate checks off (localhost only) and the **caller's** `Authorization`/cookie: the API router wraps every request in `runWithCaller`, and `loopbackGetJson` sends `callerHeaders()`. So a tide lookup must only ever happen while answering a request; one made outside that runs without a login. Never use `fetch()` for these calls. Each plugin is a `TideSource`: a 30 s deadline per call (in-process too), and a breaker that skips the plugin for 60 s after it did not answer (refused, timed out, or a redirect = wrong address) so a departure scan waits once, not per route; a 401/403/404 never trips it. Keep the deadline generous (slow Raspberry Pis): the breaker and parallel station lookups bound the wait, not a short timeout. HTTP answers are cached per login (`callerKey`), in-process ones shared. A saved remote `tidesApiBase` is warned about at start (`warnIfRemoteTidesApiBase`).

### Required `package.json` settings
1. `"keywords": ["signalk-node-server-plugin"]` — **essential** for SK server to discover the plugin via `modulesWithKeyword()`.
2. `"signalK": { "pluginConstructor": "pluginConstructor", "name": "signalk-routeiq" }` — names the factory function.
3. `"type": "module"` + `"main": "dist/index.js"`.
4. Both **named** and **default** exports must point to `pluginConstructor` — SK's `importOrRequire()` returns `module.default` for ESM.

## Routing Data Repository (signalk-router-data)
- Separate GitHub repo: `https://github.com/marcelrv/signalk-router-data`
- Contains pre-compiled `.sqlite` routing graph files in `regions/{continent}/{country}/{region}.sqlite`
- `index.json` at root is the machine-readable catalog (auto-generated by `scripts/generate_index.py`)
- `coverage-map.png` shows all available regions (auto-generated by same script)
- GitHub Action in `.github/workflows/generate-index.yml` auto-regenerates both on push
- The plugin's frontend has a "Manage Routing Data" dialog that fetches the catalog and allows downloading/updating databases
- **Autoload/disabled switch**: an installed database is switched off by renaming it to `<name>.sqlite.disabled` (`POST /databases/enabled` with `{filename, enabled}`; `DISABLED_SUFFIX` and the `isDisabledFile`/`baseFilename` helpers live in `src/data-dir.ts`). Both states are scanned and both appear in `coverageIndex` — keyed by the plain `.sqlite` name, so a toggle never changes a database's identity — but a `disabled` entry must be skipped by *every* region-selection path (`ensureRegionsLoaded`, `ensureRegionsForBbox`, `eagerLoadForPosition`, `eagerLoadIfSingle`, `loadDatabaseGraph`). `getLoadingStatus().available` counts only routable databases and reports `disabled` separately. A directory holding nothing but disabled files must still `init()` successfully with an empty graph: `GET /databases` answers 503 while `db` is null, so throwing there would leave the Data Manager unable to list — and therefore unable to re-enable — the switched-off files.
- Building or updating a database, adding POIs, or deploying to this repo is done from **signalk-router-pipeline** now, not from here — see that repo's `README.md`.

### Known issues
1. **`POST /router/push`** fails with *"PUT not supported for resources.routes.*"* — the SK server's delta PUT handler does not support writing to `resources.routes.*`. Use `putSelfPath(relPath, value, cb)` to attempt the write, but this currently returns 405.
2. **Vessel dimension subscriptions** must use `app.subscriptionmanager.subscribe(command, unsubscribeFns, errorCb, callback)` with `unsubscribeFns` as an array (not a function).
3. **`__dirname` is unavailable** in ES modules — use `new URL(import.meta.url).pathname` to derive paths at plugin-constructor scope.
